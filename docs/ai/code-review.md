# Code Review Checklist

差分レビュー時にチェックする項目。AI が PR 作成前に自己レビューに使う。`quarkus-kotlin-review` Skill から参照される。

---

## アーキテクチャ

- [ ] Resource にビジネスロジック (バリデーション・条件分岐) が混入していないか
- [ ] Service に HTTP の概念 (`Response`, `@Path` 等) が混入していないか
- [ ] Repository に業務ロジックが混入していないか
- [ ] DTO とドメインモデルが分離されているか
- [ ] 既存の層構造を **理由なく** 飛び越えていないか

---

## API 契約

- [ ] エンドポイントパスが既存の命名規約に沿っているか (RESTful)
- [ ] HTTP メソッドが意図と一致しているか (`PATCH` を `POST` で代用していないか等)
- [ ] レスポンスステータスコードが適切か
  - 200: 取得・更新成功
  - 201: 新規作成成功
  - 400: バリデーションエラー
  - 404: リソース不存在
  - 500: サーバーエラー
- [ ] レスポンス形状が DTO 経由か (ドメインモデル直渡しでないか)
- [ ] 既存 API の **シグネチャを破壊** していないか (新フィールド追加なら互換性あり)

---

## バリデーション

- [ ] 入力バリデーションが Resource 層 (アノテーション or 軽い null チェック) で行われているか
- [ ] 業務ルール (例: 価格 0 円未満) が Service 層で行われているか
- [ ] エラー時に適切な例外が投げられているか

---

## テスト

- [ ] 振る舞いを変えたなら **必ず** テストが追加・更新されているか
- [ ] 正常系・異常系・境界値の 3 つがカバーされているか
- [ ] テスト名が「何を検証しているか」を表しているか
- [ ] `./gradlew test` が緑か

---

## 安全性

- [ ] `build.gradle.kts` / `settings.gradle.kts` が変更されていないか (必要なら理由を明示)
- [ ] migrations / 永続化スキーマが変更されていないか (本講座では関係ないが本番では重要)
- [ ] 公開 API の互換性が壊れていないか
- [ ] テストを削除して通したような形跡が無いか

---

## コードスタイル

- [ ] 既存ファイルの命名・順序・インデント規約に従っているか
- [ ] `val` / `var` の選択が適切か (基本 `val`)
- [ ] null 安全性が考慮されているか (`?.`, `?:`, `!!` の乱用なし)
- [ ] 不要な import が削除されているか
- [ ] ktlint が走った状態か (PostToolUse Hook で `.kt` ファイル編集時に自動。手動なら `ktlint --format <file>`)

---

## ドキュメント

- [ ] AGENTS.md / `docs/ai/*` への影響があれば更新されているか
- [ ] 受講者向け演習ドキュメント (`docs/course/hands-on.md`) との整合性

---

```
- ...

## 残るリスク
- ...
```
